Astryx 마이그레이션 가이드

기존 Tailwind / shadcn / Radix 앱을 Astryx 디자인 시스템으로 점진적으로 전환하는 방법 · 원문: astryx.atmeta.com/docs/migration

개요

이 마이그레이션은 "전역 클래스 교체"가 아니라 "제품 셸(shell)과 워크플로우의 이전"으로 접근해야 합니다. 앱을 Theme과 AppShell로 먼저 감싸고, 기존 라우팅·비즈니스 로직은 그대로 유지한 채 한 번에 한 라우트/화면씩 Astryx 컴포넌트로 옮깁니다.

마이그레이션 중에는 Tailwind와 Astryx를 함께 사용할 수 있습니다. 레거시 래퍼나 로컬 레이아웃에는 Tailwind를 계속 쓰고, 인터랙티브 컨트롤·내비게이션·명령창·폼·알럿·다이얼로그·설정 UI는 컴포넌트로 교체합니다.

마이그레이션 순서

  1. 디자인 시스템을 설치하고 init을 실행해 패키지 스크립트, 테마 CSS, 에이전트 문서를 준비합니다.
  2. 앱 루트를 Theme으로 감싸고 초기 light / dark / system 모드 동작을 정합니다.
  3. 컴포넌트를 교체하기 전에 Tailwind와 Astryx의 CSS @layer 순서를 명시적으로 선언합니다.
  4. Foundation smoke test 페이지를 렌더링해서 프리미티브들이 padding을 유지하는지 확인합니다.
  5. 영구적인 프레임(AppShell, TopNav, SideNav, 페이지 콘텐츠, 모바일 내비게이션)부터 옮깁니다.
  6. 공유 프리미티브(Button, IconButton, TextInput, Switch, Dialog, Table 등)를 교체합니다.
  7. 전역 워크플로우(커맨드 팔레트, 설정 팝오버, 테마 토글, 검색, 필터, 생성 플로우, 파괴적 확인 다이얼로그)를 교체합니다.
  8. 완료된 화면에서 레거시 Tailwind 클래스를 제거하되, 아직 안 옮긴 부분을 위한 토큰 기반 유틸리티는 남겨둡니다.
  9. 다음 라우트로 넘어가기 전, light/dark 모드·키보드 내비게이션·반응형 레이아웃·empty/error/loading 상태를 모두 검증합니다.

CLI 워크플로우

CLI를 마이그레이션 체크리스트처럼 사용하세요. 손대려는 패턴의 문서를 먼저 읽고, 비슷한 템플릿 스켈레톤을 확인한 다음, 정확한 컴포넌트 문서를 읽고 나서 코드를 수정합니다.

# 마이그레이션 진행용 CLI 순서
npx astryx docs migration
npx astryx docs theme
npx astryx docs styling
npx astryx template --list --type block
npx astryx template AppShellTopNavWithSideNav --skeleton
npx astryx template PopoverSettingsPanel --skeleton
npx astryx component AppShell
npx astryx component SideNav
npx astryx component TopNav
npx astryx component CommandPalette
npx astryx component Button
npx astryx component TextInput

AI 코딩 도구에 결과를 붙여 넣을 때는 --dense, 자동화된 마이그레이션 리포트를 만들 때는 --json을 사용하세요.

# dense / json 모드
npx astryx docs migration --dense
npx astryx component Button --json

Theme / CSS 설정

모든 마이그레이션된 컴포넌트가 동일한 토큰 세트를 읽도록 Theme을 앱 루트에 마운트합니다. 사용자가 light/dark를 전환할 수 있다면 모드 상태를 앱 상태로 관리하세요.

// 루트 프로바이더 - 명시적 모드 관리
import {Theme} from '@astryxdesign/core/theme';
import {neutralTheme} from '@astryxdesign/theme-neutral/built';
import {useState} from 'react';
import '@astryxdesign/theme-neutral/theme.css';

export function AppRoot({children}: {children: React.ReactNode}) {
  const [mode, setMode] = useState<'system' | 'light' | 'dark'>('system');

  return (
    <Theme theme={neutralTheme} mode={mode}>
      <SettingsContext.Provider value={{mode, setMode}}>
        {children}
      </SettingsContext.Provider>
    </Theme>
  );
}

Tailwind v4와 공존

디자인 시스템의 reset/theme CSS가 Tailwind 유틸리티보다 먼저 로드되어야, 마이그레이션된 컴포넌트가 기본값을 유지하면서 레거시 유틸리티 클래스도 계속 동작합니다.

/* Tailwind v4 공존 */
@layer reset, theme, base, astryx-base, astryx-theme, components, utilities;

@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/preflight.css" layer(base);
@import "@astryxdesign/core/reset.css";
@import "@astryxdesign/core/astryx.css";
@import "@astryxdesign/theme-neutral/theme.css";
@import "@astryxdesign/core/tailwind-theme.css";
@import "tailwindcss/utilities.css" layer(utilities);

Tailwind v3와 공존

v3에는 preflight.css가 없으므로 @tailwind base 지시문을 named layer로 감쌉니다. 유틸리티는 레이어 없이 두어 기존 앱 유틸리티 클래스가 계속 우선하도록 합니다.

/* Tailwind v3 공존 */
@layer reset, tw-preflight, astryx-base, astryx-theme;

@import "@astryxdesign/core/reset.css";
@import "@astryxdesign/core/astryx.css";
@import "@astryxdesign/theme-neutral/theme.css";

@layer tw-preflight {
  @tailwind base; /* layered: astryx-theme가 preflight를 이김 */
}
@tailwind components;
@tailwind utilities; /* unlayered: 기존 유틸리티 클래스가 계속 우선 */

Cascade Layer 안전 수칙

가장 흔한 마이그레이션 장애 원인 layer() 키워드 없이 최상위에서 @import된 스타일시트는 레이어가 지정되지 않은(unlayered) 상태로 남아, 명시된 모든 @layer보다 우선 적용됩니다. 에러나 경고 없이 조용히 컴포넌트 스타일을 덮어써 버립니다.

레이어가 전혀 없는 스타일시트에서 * { padding: 0 }같은 specificity 0짜리 리셋은 어떤 클래스 선택자에도 지지만, 레이어가 도입되면 규칙이 두 번 바뀝니다: 레이어 없는 스타일은 지정된 모든 레이어를 이기고, 나중에 선언된 레이어가 이전 레이어를 이깁니다 — specificity와 무관하게요. 그래서 동일한 리셋 코드가 레이어 없이 남거나 astryx-base 뒤에 선언된 레이어에 들어가면, 모든 컴포넌트 스타일을 이겨버립니다.

/* 레거시 리셋에 레이어를 명시적으로 지정 */
/* 변경 전: @import "./legacy-reset.css";  (unlayered: 모든 레이어를 이김) */
@import "./legacy-reset.css" layer(reset);

화면을 만들기 전에 아래 체크리스트로 레이어 상태를 점검하세요.

  • 어떤 @import보다도 먼저, 표준 @layer 순서를 한 번만 선언한다. webpack 기반 번들러(Next.js 포함)는 @import 내용을 그 뒤에 오는 인라인 CSS보다 위로 끌어올리므로, 순서 선언은 layers.css처럼 별도 파일에 두고 가장 먼저 import한다.
  • 기존 전역/리셋 스타일시트를 모두 점검해서 각각 의도적으로 레이어를 지정한다. layer() 없는 최상위 import는 unlayered로 남아 모든 레이어를 이기고, 레이어가 지정된 파일 안에 중첩된 import는 그 레이어를 그대로 물려받는다.
  • 앱의 레거시 리셋을 제거하거나 reset 레이어로 낮춘다. 디자인 시스템은 자체 :where() 리셋을 가장 낮은 레이어에서 제공하므로, 앱 리셋은 같은 reset 레이어에만 있어야 하고 astryx-base보다 위 레이어에 있으면 안 된다.
  • Tailwind preflight에 레이어를 지정한다. v4는 preflight.css를 layer(base)로 import, v3는 @tailwind base를 named layer로 감싼다. 레이어 없는 preflight는 조용히 theme CSS를 덮어쓴다.
  • moduleResolution을 bundler 또는 node16 이상으로 설정해 @astryxdesign/core/reset.css같은 subpath import가 해석되도록 한다.
  • 개별 색상 토큰을 손으로 쓰는 대신 defineTheme과 accent family API로 테마를 정의한다. --color-accent만 손으로 쓰면 --color-on-accent 같은 파생 토큰이 오래된 흰색 기본값으로 남아 새 accent 색과의 대비가 보장되지 않는다.
  • 어떤 라우트를 옮기기 전에도, 아래 Foundation Smoke Test를 먼저 실행하고 light/dark 모드에서 컴포넌트 몇 개를 직접 확인한다.
기억할 것 컴포넌트에 적어 넣은 className/유틸리티 클래스는 어느 경우든 DOM에 도달합니다. 그 클래스가 컴포넌트 스타일을 이기는지는 source order 문제가 아니라 레이어 문제입니다. 앱 유틸리티는 utilities 레이어에 두어야 계속 이길 수 있습니다.

Foundation Smoke Test

레이어 순서가 깨지면 모든 페이지에서 조용히, 동일하게 실패합니다. N개 화면을 옮긴 뒤 발견하지 말고, 기능 작업 전에 먼저 잡아내세요. 첫 마이그레이션 단계로 프리미티브 몇 개를 렌더링하는 임시 페이지를 하나 만듭니다.

// Foundation check page
import {useState} from 'react';
import {Button} from '@astryxdesign/core/Button';
import {Card} from '@astryxdesign/core/Card';
import {Table} from '@astryxdesign/core/Table';
import {TextInput} from '@astryxdesign/core/TextInput';
import {VStack} from '@astryxdesign/core/VStack';

export default function FoundationCheck() {
  const [email, setEmail] = useState('');

  return (
    <div data-foundation-check>
      <VStack gap={4}>
        <Button label="Primary action" variant="primary" />
        <TextInput
          label="Email"
          placeholder="you@example.com"
          value={email}
          onChange={setEmail}
        />
        <Card>One card with default padding</Card>
        <Table
          data={[{name: 'Foundation', status: 'ok'}]}
          columns={[
            {key: 'name', header: 'Name'},
            {key: 'status', header: 'Status'},
          ]}
        />
      </VStack>
    </div>
  );
}

버튼에 눈에 보이는 padding과 filled primary 배경이 있고, input과 card에 border와 내부 spacing이 있다면 기반이 정상입니다. 테스트 러너나 dev 전용 effect에서 돌릴 수 있는 assertion은 다음과 같습니다.

// Foundation assertion
const button = document.querySelector<HTMLButtonElement>(
  '[data-foundation-check] button',
);
if (!button) {
  throw new Error('Foundation check page did not render a button.');
}
if (getComputedStyle(button).paddingInline === '0px') {
  throw new Error(
    'Foundation broken: an unlayered reset or a later cascade layer is ' +
      'overriding component styles. Check that no app reset sits outside ' +
      'the reset layer.',
  );
}

이 검사가 실패하면 원인은 거의 항상 레이어 순서입니다. padding을 0으로 만드는 스타일시트를 찾아 reset 레이어로 옮기거나 삭제하세요.

Command Palette / 설정 / 테마

셸이 갖춰진 뒤 전역 검색을 CommandPalette로 옮기세요. 팔레트는 라우트, 컨텍스트 액션, 생성 액션, 필터, 최근 항목, 엔티티 결과 등 앱 커맨드에 대한 하나의 뷰로 취급합니다. 검색 소스가 항상 검색 가능한 항목의 배열을 반환하도록 데이터 정규화는 앱 코드에서 유지하세요.

light/dark 모드 컨트롤은 설정 팝오버나 계정 메뉴에 둡니다. Switch/Selector는 독립된 body 클래스를 토글하는 대신 Theme에 전달되는 모드 값을 갱신해야 합니다.

// 설정 팝오버의 테마 컨트롤
function ThemeModeSwitch() {
  const {mode, setMode} = useSettings();
  const isDark = mode === 'dark';

  return (
    <Switch
      label="Dark mode"
      description="Use the dark color theme"
      value={isDark}
      onChange={next => setMode(next ? 'dark' : 'light')}
    />
  );
}

검증 체크리스트

  • light/dark 모드로 앱을 실행하고 surface, border, 텍스트, 아이콘, hover 상태, focus ring, 상태 색상이 자연스럽게 어울리는지 확인한다.
  • 셸에서 커맨드 팔레트를 열어 입력하고, 키보드로 항목을 선택하고, focus가 트리거로 돌아오는지 확인한다.
  • SideNav를 collapsed, expanded, active, hover, nested, mobile 상태에서 모두 확인한다.
  • 설정 팝오버와 다이얼로그를 jsdom과 실제 브라우저 양쪽에서 검증한다 (네이티브 dialog/Popover API는 테스트 shim이 필요할 수 있다).
  • 각 라우트 마이그레이션 후 남아있는 하드코딩된 Tailwind 색상, 임의의 hex 값, 일회성 hover 색상을 찾아본다.
  • 마이그레이션한 라우트마다 컴포넌트 테스트, 빌드, 최소 1회의 브라우저 스크린샷 검증을 실행한다.

AI 에이전트용 프롬프트

AI 코딩 에이전트를 쓸 때는 "전체 앱을 다시 써줘" 대신, 명시적인 마이그레이션 루프를 지시하세요.
